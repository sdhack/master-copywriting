# 反模板化层 Anti-Patternization Layer（references/anti-patternization.md）

> **Source of Truth：反模板化层 Anti-Patternization。** 主 SKILL.md 只保留简要调用；本文件是 Anti-Patternization 的唯一 Source of Truth。
> 适用范围：**所有平台、所有类型（普通/IP）、所有目的（内容/种草/卖货）的文案生成与多版本生成。**
> 解决：AI 已经能正确执行规则，但规则执行痕迹开始出现在成品里——每篇都有"我判断"、每篇都有"不过……不一定适合你"、每篇都有显式 CTA、每篇都有专业判断、每篇都有反向边界、每篇都"观点→解释→产品→CTA"、每篇长度整齐、每篇都有金句、多版本底层说话方式相同、四平台像"AI 正确执行了平台模板"。
> 本轮禁止：新增公式 / 新增钩子 / 新增心理模型 / 扩大 24 模式 / 增加复杂变量 / 为真人感堆规则 / 推翻平台中心思想。只解决一个问题：**规则在后台发挥作用，但不能让用户从成品中明显看到规则。**
> v2.8 新增：Comparison Symmetry（对比对称）、Sentence-End Amplification Check（句末强化句检查）、Set-Level QA 扩展（16.4 Evidence Check / 16.5 IP Asset Check / 16.6 Ending Check）。
> 最高原则：**规则决定质量，但规则不出现在文案里；平台有差异，但不靠平台刻板话术；IP 有人格，但不靠固定"我判断"句式；专业有边界，但不靠每篇都写"不适合"；卖货有推进，但不靠统一 CTA；多版本有差异，但不是五个模板换主题；真人感不是加入更多真人元素，而是减少 AI 过度完整、过度规则化的痕迹。**

## 一、规则性质的重新定义：Mandatory Constraint vs Optional Expression

Master Copywriting 中的规则分成两类，**禁止把 QA 检查项自动变成正文必须出现的模块。**

### 1.1 Mandatory Constraint（必须满足，但不一定显性写出来）

这些是质量底线，必须满足，但**不需要在正文中显性体现**：

| 规则类别 | 具体规则 | 检测方式 |
|---|---|---|
| 事实真实 | 产品信息不超出 Product Fact Source | Expression Authority 验收 5 问 |
| IP 不虚构经历 | 无 IP 资料不写第一人称经历 | IP Fact Firewall |
| 不越权扩展产品事实 | 不从一个卖点长出多个新卖点 | 事实扩张测试 / Expansion Budget |
| 不违反模式目标 | 完成当前 24 模式的中心心理变化 | Mode Retention Check |
| 平台原生 | 符合平台内容规律，通过平台互换测试 | 平台互换测试 / 四平台独立 QA |
| 不破坏 IP 信用 | 不为成交透支长期信任 | 换人测试 / 删除产品测试 |

**关键认知**：Mandatory Constraint 是"约束最终结果"的，不是"规定最终句子长什么样"的。例如"卖货必须包含决策信息"是 Mandatory Constraint，但"必须写一句'想试的点下面'"不是。

### 1.2 Optional Expression（只有当前内容需要时才显性出现）

这些表达元素**默认不出现**，只有当它们真正服务于当前内容目标时才出现：

| 元素 | 出现条件 | 示例 |
|---|---|---|
| 适合/不适合 | 用户差异确实明显 + 当前决策需要 + 有助于减少错误购买 + 能增强当前 IP 判断 | 产品存在明确不适用人群且与当前角度相关 |
| 反向观点/边界 | 当前判断可能存在普遍误解；边界能增强判断可信度 | 不是每篇都要"不过……" |
| 金句 | 自然融入正文，不是为金句而金句 | 正文已有鲜明判断时不强行升华 |
| 显式 CTA | 内容目的为卖货 + 平台视觉/商品卡/直播间承接不明确 | 短视频需引导点击商品卡 |
| 我的标准 | IP 判断确实需要表达为"我的标准"时 | 不是每篇都要"我选 XX 看……" |
| 用户问题 | 确有普遍场景依据，能推进内容 | 不是每篇都要"你知道吗" |
| 专业科普 | 用户需要专业知识才能决策 | 不是每篇都要"教你三招" |
| 总结 | 内容复杂需要梳理 | 短视频一般不需要 |
| 免责声明式边界 | 确有法律/信用风险需要提示 | 不是每篇都要"不一定适合你" |

**核心原则**：QA 检查项是**检查清单**，不是**写作大纲**。检查时逐项核对，写作时只写当前内容真正需要的。

## 二、Rule Visibility Test（规则可见性测试）

### 2.1 测试方法

生成后内部检查：如果用户能够明显感觉"这里是在完成 IP 判断""这里是在写不适合人群""这里到了 CTA""这里是在做专业证明""这里是在做反向克制"，则判定为**规则痕迹过重**，必须重新自然化。

| 规则痕迹 | 识别信号（用户能明显感觉到） |
|---|---|
| IP 判断模板 | "我选 XX 看……""我的标准是……""我判断 XX 的方法是……" |
| 边界模板 | "不过……""当然……""未必适合……""我不强推……" |
| CTA 模板 | "想试的点下面""链接在下面""去拍就行""点进来看看" |
| 专业证明模板 | "第一看……第二看……第三看……" |
| 结构模板 | 观点→解释→产品→适合/不适合→CTA |
| 平台模板 | "你知道吗"开头 / "姐妹们" / "中年人生感悟体" |

### 2.2 优化方法

检测到规则痕迹过重时，采用以下方法（只做删除/合并/调序/自然化，不新增模块）：

1. **融入自然叙述**：把判断融入场景或动作。"我泡这种紧压茶都先醒 5 分钟"（隐含判断）优于"我判断紧压茶需要醒茶"。
2. **改变句式**："不过不适合重口味"→"重口味的茶友可能会觉得这款偏清淡"。
3. **调整位置**：不要在结尾固定放 CTA，可在产品自然出现时引导。
4. **减少明确列举**："看三点：汤色、叶底、香气"→"泡开后先看汤色，再翻叶底，最后闻杯底香"。
5. **打破结构**：尝试问题→产品→判断、动作→观察→决策等非标准结构。

**原则：规则负责约束最终结果，不负责规定最终句子长什么样。**

## 三、禁止"专业克制模板化"

当前 AI 容易形成"前面先强判断，后面再补免责声明"：

> 看叶底就能辨好坏。不过单看叶底也不够。

这种"先绝对，再免责声明"不自然。改成**边界直接进入原始判断**：

> 我自己看这类茶，叶底会看，但一般会和汤色、香气一起判断。

即：**不要"先绝对，再免责声明"。** 边界是判断的一部分，不是判断之后的补丁。Professional Humility 的"不绝对"应该体现在判断的措辞里，而不是体现在判断之后追加一句"不过……"。

## 三·一、Comparison Symmetry（对比对称）

对比内容**禁止为了突出自己而把另一方扁平化**。

| 禁止（扁平化对比） | 推荐（对称对比） |
|---|---|
| 机器只图效率，手工才讲品质。 | 机器工艺有稳定和效率优势；我选手工路线，是因为更看重每一颗的稳定性这个具体维度。 |
| 抽湿的茶没灵魂，焙过火才是真功夫。 | 抽湿工艺出香快、成本低，有它的市场；我选焙火路线，是因为更看重茶汤的厚度和耐泡。 |

**原则：先准确理解另一种选择，再说明为什么自己选择这一边。** 这更符合专业 IP 的判断方式——承认对方有合理之处，再给出自己的取舍理由，而不是把对方说成一无是处。

检查（每处对比问）：
- 对比的另一方是否被**准确描述**（它真实存在的优势是否被承认）？
- 自己的选择是否有**具体维度**作为理由（"因为更看重 X"），而不是"我选的就是更好"？
- 对比是否**服务于当前决策**（帮助用户理解为什么选这一边），而不是为了显得自己更专业？

与 Expression Authority 的边界：Competitive Restraint（`expression-authority.md`）管"证明自己好不靠贬低别人"；本规则管"即使要对比，也必须把另一方说准确"。两者叠加：不贬低 + 不扁平化。

## 四、适合/不适合不是每篇强制模块

IP 信用需要边界感，但不代表每篇都必须写"不过如果你喜欢……那这款不一定适合"。

**只有当以下条件同时成立时才主动写"不适合"：**

- 用户差异确实明显
- 当前决策需要
- 有助于减少错误购买
- 能增强当前 IP 判断

**否则：允许不出现。**

**禁止五版文案全部出现**："不过……""当然……""未必适合……""我不强推……"。Set-Level QA 会检查：如果 3 篇以上都出现同类边界转折，且不是 IP 稳定人格，则主动打散。

## 五、IP 存在感不能只靠"我判断"

IP 内容必须有人格资产，但人格资产可以通过多种方式表现，**禁止把 IP 感固定写成"我选 XX 看……/我判断 XX……/我的标准是……"**。这些句式可以使用，但不得成为默认句式。

IP 人格资产的表现方式（至少使用一种，且多版本间轮换）：

| 表现方式 | 示例 |
|---|---|
| 选择 | 同类里我会先看这一项 |
| 动作 | 你看，我把这一颗拆开 |
| 取舍 | 我宁可少一个卖点，也不会…… |
| 拒绝 | 这种说法我一般不接 |
| 比较 | 和那种抽湿的比，这个焙过火 |
| 现场演示 | 水冲下去，你闻一下这个香 |
| 问题回答 | 很多人第一次看到都会问，为什么是方的 |
| 产品选择顺序 | 我挑水仙，先看汤色，再看叶底 |
| 什么信息不讲 | 我不跟你讲那些虚的，就看泡出来什么样 |
| 如何处理用户疑问 | 你问耐不耐泡，泡到第十五泡你自己看 |

**原则：IP 是"这个人的决策方式"，不是"每篇都有一句我的标准"。** 同一 IP 长期稳定的是价值观、判断原则、语气、对用户态度、专业边界；不应长期重复同样开场、同样转折、同样句型、同样 CTA、同样"不适合"、同样结构。**人格一致 ≠ 文案形式一致。**

## 六、Narrative Driver（内容推进动力）

Creative Variation 多版本生成时，不仅改变角度，还必须改变**内容推进动力**。候选 10 种：

| # | 驱动类型 | 定义 | 示例 |
|---|---|---|---|
| 1 | 问题驱动 | 以用户问题为起点 | "为什么别人泡的水仙比你香？" |
| 2 | 动作驱动 | 以具体操作展示为起点 | 现场拆茶、冲泡演示 |
| 3 | 判断驱动 | 以明确观点为起点 | "我挑水仙只看一个指标" |
| 4 | 现场观察驱动 | 以产品细节观察为起点 | "你们看这叶底的红边" |
| 5 | 用户决策驱动 | 以用户做选择为起点 | "你在这几款里纠结，我帮你拆" |
| 6 | 对比驱动 | 以对比为起点 | "和散茶比，方块茶差在哪" |
| 7 | 误区驱动 | 以纠正误区为起点 | "很多人以为方块茶是压碎的" |
| 8 | 使用场景驱动 | 以使用场景为起点 | "夏天带孩子出门我都泡这个" |
| 9 | 产品细节驱动 | 以产品细节为起点 | "这一颗 8 克，刚好一盖碗" |
| 10 | 结果验证驱动 | 以验证结果为起点 | "泡到第十五泡，你再看汤色" |

**规则**：生成 5 版时，至少使用 **3 种不同 Narrative Driver**。禁止 5 版全部"一个观点→专业解释→产品证明→适合/不适合→CTA"。

## 七、Structural Diversity（结构多样性）

多版本**不要求拥有相同的"组件数量"**。例如 5 版可以是：

```text
版本A：问题 → 产品 → 判断
版本B：动作 → 观察 → 决策
版本C：结论 → 解释 → 产品
版本D：场景 → 使用 → 商品
版本E：对比 → 筛选 → CTA
```

允许：

- 有的没有显式 CTA
- 有的没有"不适合"
- 有的没有金句
- 有的前半段不出现产品
- 有的直接从产品动作开始
- 有的更短

**只要：当前模式目标完成。** 结构由"当前内容需要什么"决定，不由"模板该有几个组件"决定。

---

## 八、Semantic Redundancy Check（语义冗余检查）

不要只检查字面重复，要检查**意思有没有重复**。

例如已经通过"我更看重香能不能落水"表达核心判断，后面又连续写：嘴里还有香 / 杯底有香 / 喝完还有香 / 十几泡还有香 / 不是飘一下就没。即使每句话字面不同，本质上都在证明"香持久"。

**规则：一个核心判断，最多保留 1-2 个最有画面、最有说服力的证据。第三个同类证据默认删除。**

判断方法：把每句证据翻译成它"在证明什么"，如果两句话证明的是同一个判断，只保留画面感更强、更具体的那一句。

---

## 九、字数是区间，不是 KPI

用户要求"300 字左右"，不要理解成"必须 295-305 字"。

- 如果 220 字已经自然完成，允许 220 字。
- 如果 270 字最自然，不要为了 300 字补：重复解释 / 金句 / 总结 / 免责声明 / 新卖点。

**统一原则：Natural Completion > Word Count Completion。** 除非用户明确要求严格字数（如"必须 300 字"或平台硬限制），否则以自然完成为准。字数统计口径仍按第 15 节执行。

## 十、Natural Ending（自然结束）

不是所有文案都需要一个正式结尾。

生成后：**先删除最后一句。** 如果删掉以后内容已经成立，则判断最后一句是不是只是为了以下之一而存在：

- 总结
- 升华
- 金句
- CTA
- 互动
- 模板闭环

如果是：**删除。允许自然结束。**

注意：Natural Ending 不等于"没有 CTA"。当卖货确实需要决策下一步时，CTA 属于内容的一部分而非"结尾装饰"，保留。判断标准是：删掉这句后，用户是否还知道下一步该做什么。

## 十·一、Sentence-End Amplification Check（句末强化句检查）

一个观点已经成立后，**禁止为了力度再追加"句末强化句"**。

| 禁止（句末强化句） | 说明 |
|---|---|
| ……回甘快不快、耐不耐泡，骗不了人。 | "骗不了人"是强化，删掉后观点已成立 |
| ……嘴里那股鲜甜，比我说一百句都管用。 | "比我说一百句都管用"是强化，删掉后观点已成立 |
| ……好不好自己说了算。 | "自己说了算"是强化，删掉后观点已成立 |
| ……一喝就知道。 | "一喝就知道"是强化，删掉后观点已成立 |

**检查方法：删除最后一个强化句，如果观点已经完整成立，优先删除。** 除非它确实是最自然的一句话（例如它就是当前 IP 表达判断的自然收尾），否则一律删除。

句末强化句的识别信号：骗不了人 / 一喝就知道 / 比我说一百句都管用 / 好不好自己说了算 / 你自己心里有数 / 一试便知 / 谁喝谁知道 / 一试见分晓 / 自己判断 / 自己掂量 / 值不值得。

与 Natural Ending 的关系：Natural Ending 管"最后一句是否只为总结/升华/金句/CTA/互动而存在"；本规则管"观点已成立后是否又追加了一句强化"。两者叠加：删总结句 + 删强化句，只保留真正必要的一句。

## 十一、Decision Continuation CTA（决策延续式 CTA）

CTA 不再是"文案末尾必须有一句按钮提醒"。**CTA 的本质是：当前用户决策的自然下一步。**

| 正文核心理由 | CTA 承接（顺着理由） | 禁止（统一模板） |
|---|---|---|
| "方块一颗一泡，适合嫌称茶麻烦的人" | "你平时喝茶就嫌称克数麻烦，可以从这个试试" | "想试的点下面" |
| 正文讲香 | "真正在意香落不落水的，拿一颗自己泡最直接" | "链接在下面" |
| 正文讲送礼 | "对方平时喝乌龙，再考虑这款会更稳" | "去拍就行" |

**不同内容的 CTA 理由应该不同。** CTA 必须承接本版正文的具体理由，不能与正文脱节。同批次各版 CTA 的理由、动作词、人称不得重复（Creative Variation 适用；A/B 单变量测试例外）。

---

## 十二、并非每篇卖货都必须显式 CTA

当模式是 IP 卖货，必须完成：

1. 为什么这个 IP 选择这个 SKU
2. 用户为什么值得考虑
3. 用户是否具备完成购买决定的信息

但**不一定必须写**"点击/下单/链接/下面/去拍"。如果产品承接在平台视觉、商品卡、直播间本身已经明确，可以自然结束。CTA 强度仍按第 11 节三变量路由执行，但"卖货必须有决策信息"≠"卖货必须有一句按钮提醒"。

---

## 十三、Mode Retention Check（模式保持检查）

Humanization 和 Anti-Patternization 不能导致任务模式漂移。

例如用户要求【抖音 × IP × 卖货】，即使文案非常自然，最后仍必须满足：

- 有 IP 判断或选择逻辑
- 当前 SKU 不是可有可无
- 用户理解购买理由
- 有决策信息

**漂移判定：**

| 用户看完的感受 | 判定 |
|---|---|
| 只学到知识，没有形成"为什么买这个 SKU" | 卖货 → 漂移成内容 |
| 只是"好像挺想试"，但没有决策信息 | 卖货 → 漂移成种草 |
| 种草内容变成强逼单 | 种草 → 漂移成卖货 |
| IP 内容丢失人格特征 | IP → 漂移成普通 |

必须修正。Anti-Patternization 只消除"规则痕迹"，不消除"模式目标"。

---

## 十四、平台中心思想保持 Canonical Core

禁止因为最近强调真人感而修改平台核心。继续保持：

| 平台 | 中心思想 |
|---|---|
| 抖音 | 经营注意力与观看推进 |
| 小红书 | 经营参考价值与决策价值 |
| 公众号 | 经营认知、观点与思想 |
| 视频号 | 经营信任与社交传播 |

**真人感只是质量层，不能取代平台中心思想。** Anti-Patternization 是让平台表达"不像模板"，不是让平台表达"没有差异"。

## 十五、四平台分别的防模板化规则

### 15.1 抖音

**主要防止：**
- 每篇都"你知道吗"
- 每篇都"我判断"
- 每篇都强反转
- 每篇都有免责声明
- 每篇最后"想试的点下面"
- 所有真人感都变成同一种口播节奏

**允许：**
- 有的边做边说
- 有的直接回答问题
- 有的拿产品开始
- 有的先给判断
- 有的没有正式钩子句

**核心：像同一个人不同时间拍的内容，不是同一个脚本模板换主题。**

### 15.2 小红书

**主要防止固定结构：** 标题→我的情况→优点→缺点→适合谁→不适合谁→总结。

**真实小红书笔记不需要每次这么完整。** 有些可以是：对比 / 清单 / 使用记录 / 单一问题 / 避坑 / 选择逻辑 / 购买后判断 / 单一细节。只要有真实参考价值即可。

### 15.3 公众号

**主要防止固定结构：** 故事开头→提出观点→三个论点→总结→升华。

**文章结构由"观点本身需要什么"决定。** 允许：从观点直接开 / 从现象开 / 从问题开 / 从案例开 / 从矛盾开。不要为了"像公众号"每篇都讲故事。

### 15.4 视频号

**主要防止固定结构：** 人生感悟→阅历判断→产品→克制 CTA。

**视频号的可信也可以来自：** 日常观察 / 实际经验 / 现场演示 / 用户问题 / 现实判断 / 家庭或商业场景。前提事实真实。**禁止把视频号写成固定的"中年人生感悟体"。**

## 十六、Set-Level QA（集合级 QA）

多版本生成完成后，**不能只逐篇检查，必须把所有版本放在一起检查。**

例如用户要求 5 版，检查：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否 3 篇以上都以问题开头？ | 是 → 打散开头方式 |
| 2 | 是否 3 篇以上都有"我判断/我选"？ | 是 → 打散 IP 表达方式 |
| 3 | 是否 3 篇以上都有"不过/当然"？ | 是 → 打散边界表达 |
| 4 | 是否 3 篇以上最后都是 CTA？ | 是 → 打散收口方式 |
| 5 | 是否 3 篇以上采用同一结构？ | 是 → 打散结构 |
| 6 | 是否长度几乎一样？ | 是 → 允许自然长短不一 |
| 7 | 是否每篇都有金句？ | 是 → 删除部分金句 |
| 8 | 是否每篇都有适合/不适合？ | 是 → 删除部分边界 |
| 9 | 删除前 20% 后，后 80% 是否结构相似？ | 是 → 伪多版本，重写 |

**如果某个特征在 3 篇以上重复，必须判断：它到底是 IP 稳定人格，还是 AI 模板习惯？** 如果只是模板习惯：主动打散。

### 16.1 固定选题检查（Fixed Topic Check）

Set-Level QA 必须额外检查**选题层面**是否重新模板化（完整规则见 `dynamic-angle-discovery.md`）：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否又出现"形态/香气/冷泡/避坑/送礼"固定五件套？ | 是 → 重新 Angle Discovery |
| 2 | 是否重复上一批角度（Previous Batch Exclusion 未生效）？ | 是 → 重新 Angle Discovery |
| 3 | 是否直接使用 examples 里的角度/顺序？ | 是 → 重新 Angle Discovery |
| 4 | 是否 Sell-point Skill 前 5 个卖点直接变成 5 篇？ | 是 → 重新 Angle Discovery |
| 5 | 是否 3 篇以上同属一个母题（如全部围绕"香气"）？ | 是 → Semantic Distance 重选 |
| 6 | 是否 3 篇以上只是"同一个卖点换一个场景"？ | 是 → 保留最强一版，其余重选 |

**任何一项命中：重新执行 Dynamic Angle Discovery，禁止只改标题和句子。**

### 16.2 过度稀释检查（Over-Dilution Check）

Set-Level QA 还必须检查**深度层面**是否被稀释（完整规则见 `natural-depth.md`）：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否为了 5 个不同角度而每篇只写一个知识点？ | 是 → Natural Depth 修复 |
| 2 | 是否 IP 被删弱（删除产品名后感受不到谁在说）？ | 是 → 补回 IP Asset |
| 3 | 是否卖货模式消失（漂移成内容/种草）？ | 是 → Mode Completion 修复 |
| 4 | 是否大量短句像提词器（无连续话流）？ | 是 → Conversational Flow 修复 |
| 5 | 是否内容没有达到用户要求的大致深度（300 字左右只剩摘要）？ | 是 → Depth Budget 补足 |
| 6 | 是否为了"自然结束"把成交逻辑也删掉了？ | 是 → Completion Gate 修复 |

**任何一项命中：进入 Natural Depth 修复，禁止只做句子级润色。**

### 16.3 Batch Portfolio Check（批次组合检查）

把 5 篇看成一个内容组合，检查是否形成有价值的组合而不是 5 个孤立文案：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 5 篇是否解决不同用户问题？ | 否 → 重选角度 |
| 2 | 是否使用不同的核心命题？ | 否 → 重选角度 |
| 3 | 是否有明显平台适配（平台从选题阶段介入）？ | 否 → 平台角度重选 |
| 4 | 是否存在重复母题（Semantic Distance 不足）？ | 是 → 母题去重 |
| 5 | 是否每篇都能完成当前模式（Mode Completion）？ | 否 → Depth 修复 |
| 6 | 是否有些过浅（只有结论没有支撑）？ | 是 → Depth Budget 补足 |
| 7 | 是否有些为了不同而不同（弱角度凑数）？ | 是 → 淘汰弱角度 |
| 8 | 是否都以类似节奏结束？ | 是 → 打散收口 |
| 9 | 是否有 3 篇以上结构高度一致？ | 是 → Structural Diversity 打散 |

**原则：差异性不能牺牲有效性；Novelty 不能高于 Fact Strength 和 Content Potential。**

### 16.4 Evidence Check（证据机制检查）

多版本完成后检查：**每篇主要依赖什么证据完成说服？**

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否 3 篇以上都用"自己试/自己验证/拆一颗泡/喝过就知道"作为最终信任证明？ | 是 → 打散核心证据机制 |
| 2 | 是否 3 篇以上依赖同一种证据来源（如全部靠 IP 筛选过程）？ | 是 → 打散证据来源 |
| 3 | 每篇的证据机制是否与角度匹配（选品角度用筛选过程、价格角度用价格计算、工艺角度用工艺事实、口感角度用感官描述）？ | 否 → 重新分配证据 |

证据可以来自：现场演示 / 产品事实 / 工艺 / 参数 / 价格计算 / 前后变化 / IP 筛选过程 / 对比 / 使用结果 / 用户自行验证。

**原则：稳定信用原则可以重复，表层证明方式不要重复。** "我替你们泡过几百款"可以是 IP 长期信用，但不能 5 篇都用它作为最终收口证明。Creative Variation 生成多版本时，每篇先问"这一篇主要靠什么证据完成说服"，再决定是否用"用户自行验证"作为收口。

### 16.5 IP Asset Check（IP 资产检查）

多版本完成后检查：**5 篇是否只体现同一种人物资产？**

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否 5 篇都只体现"我会选产品/我挑产品很准"？ | 是 → 为不同角度分配不同 IP 资产 |
| 2 | 是否 3 篇以上沉淀同一种人物资产？ | 是 → 打散 IP 资产分配 |
| 3 | 每篇沉淀的 IP 资产是否与角度匹配？ | 否 → 重新分配 |

IP 资产候选：选品能力 / 专业判断 / 价格观 / 做事原则 / 用户立场 / 审美偏好 / 对行业的理解 / 克制 / 诚实边界 / 服务意识 / 对复杂问题的处理方式。

**原则：人格一致 ≠ 每篇只重复同一人格资产。** 5 版 IP 内容至少体现 2-3 种不同人物资产。但不要为了多样性强行造人格，必须符合已有 IP 定位（IP Asset 分配在 Angle Discovery 阶段完成，见 `dynamic-angle-discovery.md` 七·一节）。

### 16.6 Ending Check（收口方式检查）

多版本完成后检查：**收口方式是否重复？**

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否 3 篇以上以"试一下/自己判断/链接在下面"结束？ | 是 → 打散收尾方式 |
| 2 | 是否 3 篇以上以同一种 CTA 理由结束？ | 是 → 打散 CTA 理由 |
| 3 | 是否 3 篇以上以"句末强化句"结束？ | 是 → 删除部分强化句 |
| 4 | 是否 3 篇以上以"判断留白机械句"（自己判断/自己心里有数/你自己定/你自己掂量/值不值/合不合适）结束？ | 是 → 打散收尾方式，改为承接本版具体卖点的收口 |

**原则：保留底层人格一致性，但打散表层证明和收尾方式。** 收口是当前角度完成模式的自然结果（Angle-Specific Mode Completion，见 `dynamic-angle-discovery.md` 八·一节），不是统一模板。

## 十六·五、Example Anti-Anchoring（示例不得成为选题锚点）

全面检查 SKILL.md、examples.md、platforms.md、24-modes.md、references 中所有示例：

- 如果某处长期使用"形态好奇 / 香气记忆 / 冷泡场景 / 避坑教学 / 送礼"作为五版示例，**必须削弱锚定**。
- 任何示例中的角度、顺序、标题、产品、Narrative Driver，**都仅用于解释机制，不得作为下一次生成的默认候选**。

**原则：示例是"机制演示"，不是"选题清单"。** 示例里出现的角度不得成为默认候选池。生成时若发现自己正在复现示例中的角度组合，说明 Example Anti-Anchoring 未生效，必须重新 Angle Discovery。

## 十七、区分"稳定人格"和"重复模板"

同一个 IP 可以长期稳定：

- 价值观
- 判断原则
- 语气
- 对用户态度
- 专业边界

但不应该长期重复：

- 同样开场
- 同样转折
- 同样句型
- 同样 CTA
- 同样"不适合"
- 同样结构

**即：人格一致 ≠ 文案形式一致。** 稳定人格是"这个人的决策方式"，重复模板是"AI 的执行习惯"。Set-Level QA 负责把后者打散。

## 十八、Humanization Pass 升级

Humanization 最后不再问"有没有真人感元素？"，而是问：

> **这是不是像这个人在这一次具体场景中自然说出来的？**

Humanization 只做：删除 / 合并 / 调序 / 自然化 / 动作化 / 平台化 / 去规则痕迹。

**禁止：为了满足 IP / 边界 / CTA / 金句 / 平台感，再新增一个专门模块。** 真人感不是加入更多真人元素，而是减少 AI 过度完整、过度规则化的痕迹。

## 十九、5 个最终验收问题（每篇生成完内部回答）

### 1. 目标
这一篇有没有完成当前 24 模式的中心心理变化？

### 2. 平台
如果去掉平台标签，表达方式还能体现平台原生性吗？

### 3. 人格
IP 模式下，这个人是谁，能不能感受到？

### 4. 自然
有没有明显看到模板、QA 项或规则执行痕迹？

### 5. 必要
正文中的每一块信息真的都需要吗？

**如果第五题答案是"不需要，但写了更完整"：删除。**

## 二十、最终最高原则

Skill 发展到这一阶段，不再追求"规则更多"，而追求**规则更隐形**：

- **规则决定质量，但规则不出现在文案里。**
- **平台有差异，但不靠平台刻板话术。**
- **IP 有人格，但不靠固定"我判断"句式。**
- **专业有边界，但不靠每篇都写"不适合"。**
- **卖货有推进，但不靠统一 CTA。**
- **多版本有差异，但不是五个模板换主题。**
- **真人感不是加入更多真人元素，而是减少 AI 过度完整、过度规则化的痕迹。**

一句话概括本轮迭代目标：

> **让 AI 从"会正确执行文案规则"，升级到"看不出它在执行规则"。**

## 与相邻 reference 的边界

- `final-output.md` 管**成品真人感与平台原生层**（信息减法/过度完整/自然连贯/金句限额/平台互换/Humanization Pass）；本文件管**反模板化**（规则可见性/叙事驱动/结构多样性/语义冗余/自然结束/决策延续 CTA/集合级 QA）。两者互补：final-output 解决"像不像真人"，本文件解决"看不出在按规则写"。
- `expression-authority.md` 管**事实边界**（三信息源/四级权限/IP Fact Firewall/Professional Humility）；本文件管**表达方式**。事实边界硬，表达空间宽；本文件负责把"表达空间"用得更像人。Comparison Symmetry 与 Competitive Restraint 叠加：不贬低 + 不扁平化。
- `ip-naturalness.md` 管 **IP 内容**（先写人/人格动作/专业表演感）；本文件补充"IP 存在感不只靠我判断"与"稳定人格 vs 重复模板"。
- `cta.md` 管 **CTA 路由与收口库**；本文件补充"Decision Continuation CTA"（CTA 是当前用户决策的自然下一步）与"并非每篇卖货都必须显式 CTA"。
- `platforms.md` 定义平台规律与中心思想（Canonical Core）；本文件只防平台刻板话术，**不修改平台中心思想**。
- `dynamic-angle-discovery.md` 管**讲什么**（Angle Discovery / IP Asset 绑定 / Angle-Specific Mode Completion）；本文件 Set-Level QA 的 Evidence Check / IP Asset Check / Ending Check 引用该文件完成修复。
- `natural-depth.md` 管**讲到什么程度**（Narrative Detail Boundary / Depth Budget）；本文件 Sentence-End Amplification Check 与 Natural Ending 叠加，删除总结句 + 强化句。
- `before-after-example.md` 提供 v2.5 vs v2.6 同任务 Before/After 对比示例，演示本文件各规则在成品中的落地效果。
