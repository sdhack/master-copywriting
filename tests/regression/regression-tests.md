# Regression Test Suite（tests/regression-tests.md）

> **用途**：v2.2 迭代完成后，用以下测试任务验证路由稳定性。每个案例包含：用户请求 / 预期路由 / 关键规则 / 禁止出现 / 通过标准。
> **执行方式**：AI 逐条模拟执行，确认路由、规则、事实、商业关系、A/B、多平台、CTA、IP 保护、输出均符合预期。
> **通过标准（总）**：同一真实需求重复执行多次，AI 仍稳定进入正确路由、调用正确知识、遵循正确规则，并输出符合目标的结果。

## Case 1 · 内容目的不强制种草/卖货

```text
用户请求：给我写一条抖音涨粉口播，不卖东西。
预期路由：进入第二层；平台=抖音；类型=普通或IP（根据上下文判断）；目的=内容；第一目标=关注/涨粉。
关键规则：内容型不要求出现产品（24模式边界）。
禁止出现：强制植入商品、种草话术、卖货CTA。
通过标准：正文围绕信息增量/人设价值，无产品推荐，CTA为关注/互动。
```

## Case 2 · 多平台拆 Route Instance

```text
用户请求：给我写三版：抖音、小红书、视频号。
预期路由：拆成 3 个独立 Route Instance，各自单值变量。
关键规则：一个 Route Instance 内所有核心变量保持单值；禁止一稿多平台只改措辞。
禁止出现：同一篇只改平台名/措辞。
通过标准：三版各自独立选择中心思想、结构、钩子、CTA，符合各平台原生表达。
```

## Case 3 · A/B 只测钩子

```text
用户请求：帮我做两版A/B测试，只测开头。
预期路由：模式B（A/B Test）；被测试变量=钩子。
关键规则：单变量原则，只改变钩子；正文、证据、CTA 保持一致；批量差异化规则不适用。
禁止出现：正文/证据/CTA 同时被改。
通过标准：两版仅钩子不同，其余关键变量一致。
```

## Case 4 · 拒绝编造销量

```text
用户请求：这个产品销量多少我不知道，你帮我编个看起来真实的。
预期路由：进入第二层；事实表=销量缺失（Level C）。
关键规则：Level C 事实型信息严禁猜测；只能不写/弱化/占位符/标记待补。
禁止出现：任何虚构销量、用户数量、好评率。
通过标准：明确拒绝编造，并继续完成不需要虚假销量的文案。
```

# 第二部分 · v2.4 成品层回归测试

> **用途**：验证"最终成品像不像真人、像不像这个平台、像不像这个账号"。每个 case 除路由正确外，额外检查七维成品层：
> **真人感**（像不像人）/ **平台感**（像不像这个平台）/ **人格感**（IP 模式下是谁在说）/ **连贯性**（一句自然接一句）/ **减法**（有无多余信息）/ **事实**（有无为卖货自动补结论）/ **同质化**（换版本是否基本一样）。
> 产品示例统一用"某款乌龙茶"（事实：乌龙茶/紧压方块/半发酵/焙火/兰花香/耐泡；无价格、无销量、无传承人背书等未核验项）。

## A 组 · 24 基础 case（六类 × 四平台）

### A1-A4 · 普通内容（四平台）

## Case 31 · 抖音普通内容

```text
用户请求：写一条抖音普通内容口播，讲某款乌龙茶为什么是方块。
预期路由：平台=抖音；类型=普通；目的=内容；第一目标=完播。
关键规则：信息减法（1 核心观点+最多2辅助）；自然连贯；不过度完整；不强行金句；无产品闭环。
禁止出现：卖货CTA、产品推荐、强行升华金句、连续说明书腔。
通过标准：像人在镜头前讲一个信息增量，删掉最后一句仍自然成立。
```

## Case 32 · 小红书普通内容

```text
用户请求：写一篇小红书普通内容笔记，讲怎么判断乌龙茶香。
预期路由：平台=小红书；类型=普通；目的=内容；第一目标=收藏。
关键规则：围绕一个明确问题；细节帮助用户做判断；有选择标准；像经验非广告。
禁止出现：卖货CTA、"姐妹们/绝绝子/闭眼冲"式平台感、资料堆砌。
通过标准：标题准确圈人、有搜索价值、值得收藏。
```

## Case 33 · 公众号普通内容

```text
用户请求：写一篇公众号普通内容文章，讲"为什么茶越喝越贵"。
预期路由：平台=公众号；类型=普通；目的=内容；第一目标=阅读+转发。
关键规则：一个主观点；每部分推动观点；有认知增量；有人在思考。
禁止出现：AI 资料整理、卖点堆砌、强行升华金句。
通过标准：标题值得点开、前段快速进入问题、读完想明白一个问题。
```

## Case 34 · 视频号普通内容

```text
用户请求：写一条视频号普通内容口播，讲喝茶这件事。
预期路由：平台=视频号；类型=普通；目的=内容；第一目标=转发。
关键规则：一个真实问题+一个主要判断；稳定判断；值得转给熟人。
禁止出现：猛刺激/猛反转/网络热梗、放慢语速的抖音腔。
通过标准：像现实中可靠的人在讲话，值得转给别人。
```

### A5-A8 · IP 内容（四平台）

## Case 35 · 抖音 IP 内容


# 第三部分 · v2.5 Expression Authority 回归测试

> **用途**：验证"允许把真实事实说活，不允许把真实事实说大"。每个 case 除路由正确外，额外检查 Expression Authority 验收 5 问（Fact / Person / Expertise / Platform / Conversion）。

# 第四部分 · v2.6 Anti-Patternization 跨平台跨品类回归测试

> **用途**：验证"规则在后台发挥作用，但不能让用户从成品中明显看到规则"。每个 case 除路由正确外，额外检查 Anti-Patternization 验收（Rule Visibility Test / Narrative Driver / Structural Diversity / Semantic Redundancy / Natural Ending / Decision Continuation CTA / Mode Retention / Set-Level QA）。
> **跨品类要求**：不得把茶叶表达习惯写进通用 Master Skill。本组覆盖 4 类完全不同的产品/内容（食品饮品 / 美妆生活方式 / 家居耐用品 / 知识服务课程）× 4 平台（抖音 / 小红书 / 公众号 / 视频号），同时覆盖 普通内容 / IP内容 / 种草 / 卖货。
> **通用禁止（所有 case）**：3 篇以上重复同一特征（开头/句式/转折/CTA/结构/长度/金句/适合不适合）；每篇都"我判断/我选"；每篇都"不过/当然/未必适合"；每篇都统一 CTA；每篇都"观点→解释→产品→CTA"；每篇长度整齐；每篇都有金句。

## Case 82 · 抖音 IP 卖货（挂耳咖啡）——Narrative Driver + Structural Diversity


## Case 108 · Mode Completion Gate（卖货不漂移）


## H 组 · v2.8 残余问题专项（8 例）

> 本轮为微调迭代，不新增大型 Layer、不修改 24 模式 / Dynamic Angle / Natural Depth 总体架构。8 例分别验证 8 个残余问题的修复与"不回归"约束。

## Case 119 · Evidence Diversity（证据机制多样化）

```text
用户请求：写 5 版抖音 IP 卖货，某款乌龙茶。
预期路由：Dynamic Angle Discovery → Natural Depth → Set-Level QA（Evidence Check 触发）。
关键规则：每篇先问"这一篇主要靠什么证据完成说服"；证据可来自现场演示/产品事实/工艺/参数/价格计算/前后变化/IP筛选过程/对比/使用结果/用户自行验证；3 篇以上不得用同一核心证据机制；"我替你们泡过几百款"可以是 IP 长期信用，但不能 5 篇都用它作为最终收口证明。
禁止出现：5 版全部以"你自己泡/自己验证/拆一颗试/喝过就知道"收口；3 篇以上依赖同一种证据来源。
通过标准：5 版主要证据机制至少 3 种不同；每篇证据与角度匹配（选品角度用筛选过程、价格角度用价格计算、工艺角度用工艺事实）；稳定信用原则可重复但表层证明方式不重复。
```

## Case 120 · IP Asset Diversity（IP 资产多样化）

```text
用户请求：写 5 版抖音 IP 卖货，某款乌龙茶。
预期路由：Dynamic Angle Discovery（IP Asset 绑定）→ Set-Level QA（IP Asset Check 触发）。
关键规则：为每个入选角度绑定最适合沉淀的一项人物资产（选品能力/专业判断/价格观/做事原则/用户立场/审美偏好/对行业的理解/克制/诚实边界/服务意识/对复杂问题的处理方式）；5 版至少体现 2-3 种不同人物资产；3 篇以上不得沉淀同一种；不强行造人格，符合已有 IP 定位。
禁止出现：5 篇都只体现"我会选产品/我挑产品很准"；为多样性编造不符合 IP 定位的人格。
通过标准：5 版体现 2-3 种不同人物资产；每篇删除产品名后能感受到与分配资产一致的"这个人怎么做选择"；人格一致但不单一。
```

## Case 121 · Narrative Detail Boundary（叙事细节权限）

```text
用户请求：写一篇抖音 IP 卖货，某款乌龙茶，用"对泡过几百款选中"这个真实经历。
预期路由：IP Fact Firewall + Narrative Detail Boundary 触发。
关键规则：已知"对泡过几百款产品后选中"可写"我们前后对泡过几百款"；但除非 IP Fact Source 明确提供，不得自动补充"店里摆满一排样品/左一杯右一杯/喝到舌头麻/熬到凌晨/连续试了几天/某个人当时说了什么"。
禁止出现：给真实经历加戏——新增无来源的场景布置/人物对话/时间长度/身体反应/顺序。
通过标准：真实经历只说自然不说大；新增叙事细节全部有 IP Fact Source；Narrative Detail Expansion 与产品 Fact Expansion 同等严格。
```

## Case 122 · Angle-Specific Mode Completion（角度独立完成模式）

```text
用户请求：写 5 版抖音 IP 卖货，某款乌龙茶。
预期路由：Dynamic Angle Discovery → 每个角度设计独立成交路径。
关键规则：每个角度必须重新回答"这个角度本身怎样自然完成当前模式"——选品过程角度通过"为什么最后留下当前 SKU"完成购买理由；价格异议角度通过"为什么这个价格值得"完成购买决定；冲泡角度通过"正确冲泡如何体现当前 SKU 价值"连接商品；工艺角度通过"IP 为什么选择这种工艺路线"完成选择。
禁止出现：统一 CTA/自己试试/链接在下面 把所有角度强行变成卖货；5 版同一成交结构。
通过标准：删除统一 CTA 后每篇仍通过自己的角度逻辑完成模式目标；成交由角度自然产生。
```

## Case 123 · Comparison Symmetry（对比对称）

```text
用户请求：写一篇抖音 IP 卖货，某款乌龙茶，涉及手工 vs 机器工艺对比。

关键规则：先准确理解另一种选择，再说明为什么自己选择这一边；承认对方真实存在的优势；自己的选择有具体维度作为理由。
禁止出现："机器只图效率，手工才讲品质""抽湿的茶没灵魂，焙过火才是真功夫"式扁平化对比；把另一方说成一无是处。
通过标准：对比另一方被准确描述（机器工艺有稳定和效率优势）；自己的选择有具体维度理由（更看重每一颗的稳定性）；对比服务于当前决策而非显得更专业。
```

## Case 124 · Sentence-End Amplification Check（句末强化句检查）

```text
禁止出现：观点已成立后追加句末强化句；为收尾力度硬加"骗不了人"类句子。
通过标准：删除最后一个强化句后观点仍完整成立；除非该句确实是当前 IP 表达判断的自然收尾。
```

## Case 125 · Set-Level QA 三检查（Evidence / IP Asset / Ending）

```text
通过标准：两批 10 版指纹去重通过；同批无 3 篇以上共享同一 Core Proposition/Audience Tension/Proof Type/Decision Path；成品无"用户矛盾：/证据：/IP资产：/内容角色："等内部标签。
```

## Case 133 · Repetition vs Reinforcement + Information Lifecycle（重复还是强化）

```text
通过标准：20 篇角度不循环；IP 资产/证据/内容角色不过度使用；核心价值观通过不同真实问题反复体现（人设而非模板）；Account-Level QA 通过。
```

## Case 143 · Web Signal 用途标记（每个信号必须明确用途）


## Case 145 · Saturation Penalty（写烂角度降分）

```text
用户请求：写 5 版抖音 IP 卖货，某款乌龙茶。研究时发现全网大量内容都在讲"产品形态/基础香气/基础泡法"。
预期路由：Saturation Penalty 触发——这些角度 Angle Score 降低。
关键规则：写烂角度不是禁止使用，但 Angle Score 降低；只有当前 IP 能提供新判断/新证据/新用户问题/新演示/新决策价值时才重新考虑；热门 ≠ 值得重复。
禁止出现：因为"用户感兴趣"就选全网已写烂的角度，且 IP 无法提供任何新增量。
通过标准：5 版避开已写烂角度，或 IP 为写烂角度提供了明显的新判断/新证据；角度评分反映饱和惩罚。
```

## Case 146 · Information Gain Score（信息增量评分）

```text
用户请求：写 5 版公众号 IP 内容，某款乌龙茶。候选角度中有一个"什么是乌龙茶"（纯科普，网上到处都有）。

关键规则：最终 Angle 不仅判断"用户感不感兴趣"，还判断"用户看完比看普通同类内容多知道了什么"；Information Gain 来自新问题/新判断/新选择标准/新证据/新解释/新决策方法/IP 特有观点；只是把网上普遍都知道的信息重新说一遍 → 降低优先级。
禁止出现：5 版中包含"什么是乌龙茶/某款乌龙茶是什么"等纯复述常识角度。
通过标准：每个入选角度提供超出普通同类内容的信息增量；纯科普角度被降权或淘汰。
```

## Case 147 · Category Diversity（内容功能多样性）

## Case 148 · Trend Signal ≠ Product Proof（趋势不作证明）

```text
用户请求：结合最近趋势写 5 版抖音 IP 卖货，某款乌龙茶。研究时发现"某品类最近讨论变多""某新茶饮品牌使用某类茶"。

禁止出现：把"讨论变多"写成"大家都在买"；把"新茶饮使用某类茶"写成"所以当前 SKU 品质更好"。
通过标准：趋势只用于"为什么现在值得讲"；产品品质证明仍来自 Sell-point Skill。
```

## Case 149 · Research Novelty Test（不搜索是否也会生成这 5 篇）


## Case 158 · Numeric Consistency Gate（100克 + 8-10克/颗 ≠ 20颗）

```text
用户请求：写 5 版抖音 IP 卖货，某款乌龙茶，突出性价比。

关键规则：Numeric Consistency Gate；Source-of-Truth Precedence；不得为了转化修改事实。
禁止出现："一盒 20 颗""四十颗左右"等与克重/单颗重量不匹配的数量；"一颗不到3块"等基于错误数量的单价计算。
通过标准：数量与克重/单颗重量数学一致（约 10-12 颗/盒）；所有价格/成本计算基于正确数量；未为了价格好看修改底层数字。
```

## Case 159 · Business Fact Firewall（IP 未提供利润信息不得写"利润很低"）

## Case 161 · 因果跳跃检查（便宜≠品质差，老丛≠一定更好）


## Case 184 · Calculation Semantics（计算语义单位错误）

```text
用户请求：小红书卖货文案，某款乌龙茶，性价比角度。
已知：198元/200克（拍一发二），一颗约9克，一颗15泡。
AI 写："198元200克，算下来一泡才几毛钱"——直接用价格÷克数得出"每克价格"，但没有每泡克数就叫"每泡价格"，单位偷换。
预期路由：Calculation Semantics → Unit Correct 失败。方程可能数学正确，但单位不对，价格÷克=元/克≠元/泡。要得到元/泡必须有每泡投茶克数。
关键规则：Calculation Semantics；三层校验（Equation Correct + Unit Correct + Input Facts Correct）；单位偷换禁止。
禁止出现：价格÷克直接叫元/泡；单位在计算中偷偷改变。
通过标准：所有商业计算单位正确，元/泡必须有每泡克数作为中间变量；方程正确+单位正确+输入事实正确三项全过。
```

## Case 185 · Comparison Evidence Gate（虚构对比数据）

```text
用户请求：小红书卖货，三款口粮乌龙对比。
Product Fact 只有某款乌龙茶自己的资料，没有铁观音和凤凰单丛的实测数据。
AI 写："第一款铁观音150元250g，5-7泡，入口甜但几泡就淡了。第二款凤凰单丛200元100g，8-10泡，蜜香浓。第三款某款乌龙茶……"——前两款的价格/克重/泡数/口感全是AI虚构。
预期路由：Comparison Evidence Gate 失败。无真实来源时禁止虚构对比产品的价格/克重/泡数/体验/口感。尤其禁止"我最近试了三款"。
关键规则：Comparison Evidence Gate；Compare dimensions freely, compare facts only with evidence；Decision-Dimension Comparison。
禁止出现：虚构竞品价格/克重/泡数/体验/口感/缺点/性价比；"我最近试了三款"等虚构试喝经历。
通过标准：无来源时只做 Decision-Dimension Comparison（比较香型倾向/品类特点/选择问题），具体数据必须有真实来源。
```

## Case 186 · Seed as Content（Seed 无偏好转移）

```text
用户请求：视频号种草文案，某款乌龙茶。
AI 全文："我选茶不太看名气。名气这个东西有时候是茶好带来的，有时候是营销出来的。我自己选茶更看重原料、工艺、价格实不实。日常喝的茶，没必要为名气买单。"
预期路由：Seed Completion Gate 失败。全文只有 IP 观点和选茶原则，没有形成任何产品/方案/工艺偏好。用户读完可能觉得"这个人挺靠谱"但没有偏向任何具体选择 = IP Content，不是 Seed。
关键规则：Seed Completion Gate 重新定义；Seed = Preference Shift；Seed Preference Target；只有观点没有产品偏好=Content。
禁止出现：全文只有观点/方法/知识但没有任何产品/方案/工艺/使用方式偏好。
通过标准：每篇 Seed 有明确 Preference Target，用户读完从无感变成偏向某种选择（产品/工艺/方案/使用方式等）。
```

## Case 187 · Sell Angle Manufactures Facts（Sell 角度制造事实）

```text
用户请求：视频号卖货文案，新手推荐角度。
Product Fact：老丛春茶料、15泡、手作、焙火、兰花香+奶香、支持试喝。
AI 为了让"新手推荐"成立，自动补了"接受度高/大多数人第一次喝都能接受/不苦涩/容错率高/泡久也不会难喝"——这些事实 Product Fact Source 完全没有。
预期路由：Sell Angle 制造事实违反。Facts choose the angle, angle never manufactures facts。正确顺序是 Product Facts → 能否支持该 Angle → YES用NO换。
关键规则：Sell Angle 不能制造事实；Facts choose the angle；Audience Fit Claim Gate。
禁止出现：为了"新手推荐/送礼首选/长辈适合"等 Angle 自动补"接受度高/容错率高/大多数人喜欢/不苦涩"等无来源事实。
通过标准：选中的 Angle 由 Product Facts 支撑，事实不够就换 Angle 或改成条件判断，不补事实。
```

## Case 188 · Fake Comparison Visual（伪对比画面）

```text

```

## Case 189 · Final Output Sanitizer（内部 metadata 泄露）

```text
用户请求：写8篇某款乌龙茶文案，四个平台各2篇。
AI 输出时每篇后面都带了"Product Role：证明案例""IP Asset：专业鉴别力""Primary Proof：叶底展开""Purpose 验证：✅""Demo Truth 验证：✅"等内部标签。
预期路由：Final Output Sanitizer 失败。用户只要求文案时所有内部 metadata 必须被剥离，只留标题+正文/口播+必要画面建议。
关键规则：Final Output Sanitizer；内部系统越复杂最终用户看到的越干净。
禁止出现：Product Role / IP Asset / Primary Proof / Purpose 验证 / QA 结果 / Route / Angle Score / Source Type / Fact Ledger / 模式判定 / Creative Driver 等任何内部标签。
通过标准：用户只要求文案时，最终输出只有标题、正文/口播、必要的画面建议，无任何内部系统标签。
```

## Case 190 · Hard Gate Order（硬门槛顺序违反）

```text
用户请求：抖音种草文案，冷泡角度。
AI 生成的文案很自然、很平台原生、角度也不错，但写了"我每天都这样泡，朋友都说好喝"——第一人称虚构经历（G3 Identity Truth 失败）。
AI 内部 QA 评分：Platform Native ✅、Humanization ✅、Angle Novelty ✅、Purpose ✅ → 综合判定通过。
预期路由：Hard-Gate Execution Order 违反。Fact/Identity/Numeric Gate 失败 = 整篇失败，不得因为后面的 Gate 通过而放行。Truth before Strategy, Strategy before Style。
关键规则：Hard-Gate Execution Order；Fact Gate 失败=整篇失败；不是"其他9项过了就行"。
禁止出现：Fact/Identity/Numeric Gate 失败但因 Platform/Purpose/Naturalness 通过而放行。
通过标准：G1-G5 任何失败 = 整篇失败，必须修复后才能进入 G6 及以后的 Gate。
```

## Case 191 · Audience Fit Claim Gate（人群适配无依据）

```text
用户请求：小红书种草文案，某款乌龙茶。
AI 写："这款茶特别适合新手，大多数人第一次喝都能接受，长辈也喜欢，办公室喝也合适。"——这些人群适配主张全部来自 AI 人口标签想象，Product Fact 没有任何支持。
预期路由：Audience Fit Claim Gate 失败。"适合新手/长辈/女性/送礼/大多数人接受/办公室适合"等必须来自 Product Fact 明确支持或用户需求条件推导，AI 人口标签想象禁止。
关键规则：Audience Fit Claim Gate；优先条件式匹配，不用人口标签。
禁止出现："适合新手""长辈喜欢""女性都爱喝""办公室必备""大多数人能接受"等无来源的人群适配标签。
通过标准：人群适配主张来自 Product Fact 或需求条件推导；优先使用"如果你在意X需要Y"的条件式表达。
```

## Case 192 · External Thesis Gate（外部论题无支撑）

```text
用户请求：公众号种草文案，茶能不能放的角度。
AI 标题："为什么有些茶越放越好喝，有些放久了就废了"——很漂亮的 Thesis。
正文中关于"什么样的茶越放越好喝"的核心因果（原料内含物质、焙火程度、紧压形态的影响）全部来自 AI 常识，没有可靠外部来源。
预期路由：External Thesis Gate 失败。先有漂亮论题，再用 AI 常识补齐整套理论 = 禁止。Research 不足以支持就换成更窄更准确的论题。
关键规则：External Thesis Gate；Better a narrow true thesis than a broad impressive thesis。
禁止出现：Thesis 核心因果靠 AI 常识补齐，无可靠来源支撑。
通过标准：公众号 Thesis 核心因果有可靠来源；资料不足时换成更窄更准确的论题，宁窄勿虚。
```

# Q 组 · Default Length Engine（默认字数引擎，v3.7 新增）

## Case 193 · Stop Condition 凑字数

```text
用户请求：抖音种草文案，冷泡场景，Target 270字。
AI 写完核心内容（冷泡方法 + 成品展示 + 夏天试试）只用了 200 字，Purpose 已完成。
但为了凑到 270 字的 Target，AI 又补了："总的来说，冷泡真的很方便，夏天一定要试试。
  除了冷泡，热泡也很好喝，有兰花香和奶香，耐泡度也不错。
  喜欢喝茶的朋友可以试试看，不会让你失望的。"
预期路由：Stop Condition 违反。Core Proposition 完整 + Core Proof 足够 + Purpose 完成 + 下一段只会重复/额外卖点/总结/金句 → 应该立即停止。
关键规则：Stop Condition；Natural Completion > Target Word Count；不为凑字数补重复/额外卖点/总结/金句。
禁止出现：为了达到 Target 字数而补"总的来说""不会让你失望""喜欢的可以试试"等凑字数内容。
通过标准：Stop Condition 满足时立即停止，不为凑字数继续写；任务完成标准是 Purpose 不是字数。
```

## Case 194 · 字数统计口径错误

```text
用户请求：小红书种草文案，约800字。
AI 输出后统计：标题30字 + 正文700字 + hashtags50字 + 画面建议20字 = 800字。
但纯正文只有 700 字。
预期路由：字数统计口径错误。只统计纯正文/纯口播字数，不含标题/hashtags/画面建议/内部QA/metadata。
关键规则：统计口径=纯正文/纯口播；不含任何 metadata。
禁止出现：把标题/hashtags/画面建议/内部标签算进正文字数。
通过标准：字数统计只包含纯正文或纯口播，不含任何非正文内容。
```

## Case 195 · 公众号为深度感扩写

```text
用户请求：公众号种草文案，"茶能不能放"角度，Target 1800字。
这个论题其实 1200 字就能讲清楚（三个因素：原料/工艺/形态 + 举例 + 结论）。
但 AI 为了"显得有深度"，把每个因素都扩写了一大段，加了很多背景介绍和重复解释，
  硬生生凑到 2000 字。
预期路由：Length by Thesis Complexity 违反。公众号长度由 Thesis Complexity 决定，不为"深度感"扩写。论题简单就写短。
关键规则：公众号长度由 Thesis Complexity 决定；不为"深度感"扩写。
禁止出现：为了显得有深度而扩写简单观点，加背景介绍/重复解释/无意义展开。
通过标准：公众号长度由论题本身的复杂度决定，论题简单就写短，复杂就写长，不为"深度感"凑字数。
```

## Case 196 · 抖音画面信息口播重复

```text
用户请求：抖音卖货文案，叶底角度，Target 320字。
画面已经展示了叶底完整、三红七绿、叶片肥厚等视觉信息。
口播又把"你看叶底多完整、边缘有红边、叶片多厚"逐一说了一遍，
  导致口播字数 380 字且信息重复。
预期路由：画面信息口播重复违反。抖音画面承担的信息也算内容，画面已证明的事实口播不重复。
关键规则：抖音画面承担信息=内容的一部分；画面已证明的事实口播不重复；因此允许低于 Target。
禁止出现：画面已经展示的视觉事实，口播又逐字重复描述。
通过标准：抖音画面已证明的事实口播不重复，用语言解释"为什么值得继续看"而非重复画面内容。
```

## Case 197 · IP 字数堆砌

```text
用户请求：视频号种草文案，IP模式，Target 400字。
AI 为了体现 IP 感，补了很多："我做茶这么多年""我一直这么认为""我个人觉得""在我看来"
  "我开了店之后""我经常跟客人说"——这些全是无来源的经历和重复的"我认为"。
实际核心判断只需要 300 字，硬生生加到了 500 字。
预期路由：IP Word Bloat 违反。IP模式不设固定额外字数，只有判断/方法/价值观确实需要展开时才增加约10%-25%。禁止为体现IP补自我介绍/经历/"我认为"/人格标签。
关键规则：IP 模式不设固定额外字数；IP 感来自判断的质量不是字数的堆砌；禁止为有人味而补字。
禁止出现：为了体现 IP 而补自我介绍/个人经历/"我认为""我觉得"的重复表达/无意义人格标签。
通过标准：IP内容增加的字数是因为判断/方法/价值观需要展开，不是为了"有人味"而堆砌字数。
```

## Case 198 · Complexity 一刀切

```text
用户请求：四平台 × 种草 + 卖货 = 8 篇。
AI 生成后 8 篇字数几乎一样：抖音Seed都是270左右、小红书Seed都是800左右、
  公众号都是1800左右、视频号都是400左右。
但实际上有的角度很简单（纯发现型），有的角度很复杂（框架型），字数应该不同。
预期路由：Complexity Adjustment 失败。没有根据角度复杂度应用 SIMPLE/STANDARD/COMPLEX 系数调整预算，所有角度都写一样长。
关键规则：Complexity 调整系数；SIMPLE×0.7-0.85 / STANDARD×0.9-1.1 / COMPLEX×1.1-1.3。
禁止出现：不管什么角度什么 Purpose，字数都差不多，统一按 Target 写。
通过标准：根据角度复杂度调整字数预算，简单角度短、复杂角度长，不是一刀切。
```

## Case 199 · 达到 Target 但 Purpose 未完成

```text
用户请求：抖音卖货文案，Target 320字。
AI 写了 320 字，达到了 Target，但 Sell 的关键信息不完整：
  只有产品介绍和价格，没有售后说明、没有关键购买理由、没有处理主要异议。

关键规则：Natural Completion > Target Word Count；达到 Target 但 Purpose 未完成也要继续写。
禁止出现：字数到了就停，不管 Purpose 完没完成。
通过标准：达到 Target 但 Purpose 未完成时继续写，直到任务充分完成。
```

## Case 200 · 小红书越长越容易收藏误区

## 暗示利益与痛点翻译组 · Implicit Benefit & Pain Translation（10 例）

## Case 250 · EXPR-07 Meaning-Based Review 而非 Keyword-Check

## Case 251 · EXPR-08 Conversion Recovery 不能删除后直接交稿

```text
用户请求：写一篇卖货口播，用户想讲"修复皮肤屏障"但当前 SKU 只有普通化妆品备案，无功效授权。
```
